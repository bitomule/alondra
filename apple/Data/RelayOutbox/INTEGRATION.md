# Relay outbox integration

`AlondraRelayOutbox` is the durable boundary around `AlondraRelayClient.submit`. It takes an already sealed `EnvelopeV1`, validates its framing and the expected Mac/phone route, writes it to a protected file, then permits exactly one POST attempt for that request ID. A lost response, process death, 502 after dispatch, or disk failure after POST leaves an uncertain record. No path in this module replays a POST. `reconcile(requestID:)` only calls GET status and persists the latest observed job and encrypted response.

The outbox scope must contain the relay URL, paired Mac ID, phone device ID, and a durable credential revision that changes on account or device-key replacement. Construct a new scope and discard live sessions on login/logout, account change, Mac replacement, or key rotation. An entry from another scope cannot be read or reconciled through this instance. The caller must also verify the response envelope against the pinned Mac key, recipient, route, request ID, kind, and epoch before applying data. This module deliberately does not decrypt or grant authority.

The file is ciphertext-only and uses atomic writes, file protection, and an advisory file lock around each transaction so the app and a future extension cannot reserve the same request ID twice or overwrite each other's records. Put it in a shared App Group location only after the extension has the same scoped credentials and the physical-device MAV gate proves cold-start access while locked. File protection can deny a cold background read; fail closed and surface an unresolved action rather than sending again. Keep the protected file out of backups if the app's backup policy requires it.

`CommandGate` remains the UI conflict/uncertainty guard. The service use case must reserve both the semantic command and the sealed outbox entry before sending, and must not mark the command confirmed merely because the relay returned 202: completion requires a final job plus verified, decrypted Mac response and reconciliation against authoritative state. A 502 `response_too_large` after Mac dispatch is uncertain even when the relay POST itself returned successfully. Do not expose any mutation through a view or notification extension until that composition is covered by a relaunch test and MAV.

After the H service verifies and durably applies a completed Mac response, it may call `retireAppliedResponse` with the observed revision and exact verified envelope. This removes the large encrypted bodies but retains a small request-ID tombstone, so accidental reuse cannot POST again. `reconcile` returns nil for a retired entry, including when a concurrent status request finishes after retirement; inspect `entry` to distinguish that tombstone from an unknown ID. An expired or uncertain operation cannot be retired this way; reconcile it against authoritative Mac state first. The service must budget for tombstones over time and must never discard unresolved entries by age alone. No upload path is defined by the current relay allowlist.

Run `bazel test //apple/Data/RelayOutbox:AlondraRelayOutboxTests`. The integration tests exercise durable-before-POST ordering, relaunch without repost, read-only reconciliation, retirement with a tombstone, corruption fail-closed, account-scope rejection, competing outbox instances, pre-POST validation, and controlled status/timeout races.
