# Settings integration (H)

- `AlondraiOSEntry` already links `AlondraSettingsFeature`. The two existing sheets still instantiate `SettingsView()`; H moves it into the root feature.
- `SettingsView` installs the live `SettingsConnection` at its composition boundary. The feature owns draft URL, check state, cancellation and save decision. `SettingsLive` creates the candidate `AlondraClient` using `DevicePairing.signer(for:)`; the signer remains scoped to the candidate server. Saving writes the existing `serverURL` key, which `AlondraApp` observes and forwards to `IOSAppSync.use(serverAddress:)`. H should move this adapter into the app composition owner when Settings becomes a root child.
- Pairing and push sections remain UI adapters to their existing services. H should route their actions through the root reducer and Data use cases, then remove the direct `DevicePairing`/`PushCenter` environment use from this view. Do not move push response handling into Settings; the notification path must run without UI.
- A future iOS 0.1 login section should inject a separate OIDC authentication use case. Its agreed contract is issuer `https://alondra-auth.davidcollado.dev/realms/alondra`, client ID `alondra-ios`, redirect `com.bitomule.alondra:/oauth2redirect/keycloak`, authorization code with PKCE S256 and `openid profile` scope. The relay requires a JWT with audience `alondra-relay` **and** the signature of a paired device. Login state must not silently grant device authorization or expose a signer to feature state. This branch intentionally leaves the OIDC implementation to the authentication workstream.
