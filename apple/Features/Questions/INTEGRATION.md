# G1 Questions and documents — H integration contract

`AlondraQuestionsFeature` owns question/action drafts, report/document review comments, selected protocol option, load/send state, and visible conflict/permission errors. It contains no HTTP, URLSession, client, signer, keychain, or view dependency. iOS and Mac can present their own SwiftUI views backed by `QuestionFeature`, `ActionFeature`, and `DocumentReviewFeature`; views send actions and render state. `DocumentReviewFeature` supplies the combined Markdown source for inline content and every stored text attachment, with filename headings so comments have context. Binary attachments remain metadata in the parent UI and are never requested from the text endpoint.

The parent must create one child state per card in the current scene. On an overview refresh, send `.refreshed` to a child with the same stable ID so typed text, selected option, attached stored IDs, and comments survive. When a card is withdrawn or a different card is selected, remove the old child. A changed document source clears anchored comments; reloading changed content at the same path does the same. Send `.appeared` when a document is reopened to revalidate its content. On service/credential identity changes, send `.identityChanged` or recreate the child before showing another identity's data. These reducers guard late effects with a monotonic revision; scene scope owns their lifecycle.

Use F1's `TriageFeature.State.questions(forPullRequest:)` and `reports(forPullRequest:)` to display PR children. Do not add those IDs as independent inbox cards or re-derive the grouping. G2 should use the same F1 map for its PR detail. The card id is `q<id>` or `r<id>`; `prId` is the parent link.

Install `QuestionWorkService` at the app/scene composition boundary. Its ordinary `submit` closure handles `.answer`, `.moreContext`, and `.reviewReport` through the process-owned `CommandGate`, mapping HTTP 409 to `.conflict(reason)`. `submitReportFeedback(request, identity)` is a *single semantic operation*: the reducer calls it once and never coordinates the message and mark-read steps or retries a message. H/Data must implement a separate durable transaction before enabling this control. Reserve a checkpoint before network I/O, keyed by server, device, credential revision, report ID, and a persisted operation ID. Persist a `messageSentAwaitingRead` stage after a confirmed message and before mark-read. A crash or persistence failure in the gap must leave an unknown checkpoint that prohibits resending until reconciled. On relaunch, resume mark-read from the sent stage without resending the message; unknown sends require authoritative reconciliation. Remove the checkpoint only after read confirmation. The current `FileCommandJournal` removes confirmed records and is insufficient by itself. Add a restart integration test with a new service/journal instance after message 200 and failed mark-read; prove one message send, then read completion. The feature tests use a fake coordinator across recreated Stores to verify only the reducer contract, not disk durability. The default service returns unavailable, so report feedback must remain disabled until that H/Data integration is complete.

An uncertain outcome blocks edits and sends until H reconciles the journal and snapshot and sends `.reconciled(...)` with an authoritative open/closed result. A mere overview refresh must not send that action. `DocumentReviewFeature` blocks feedback and review while content is loading or has a load error; platform views should show those states and not present stale source text. The service's `document` closure fetches a stored text path through the authenticated service and checks scope. Attachment upload belongs to an app-level file service; only *stored identifiers* enter feature state. Do not pass file bytes or local paths into reducers. `QuestionOperation` is a local-daemon command description, not a cloud relay HTTP endpoint. For terminal menus (`toolUseId` begins `menu:`), show only exact option buttons; hide free-text, attachment, and more-context controls.

The cloud relay exposes opaque E2E request transport, not direct `/v1/questions` or `/v1/reports` routes. H's RelayClient adapter must pair/authenticate the device and wrap allowed local operations in signed, encrypted envelopes. Backend PR #156 (tip `1bcd9df`) expands the Mac allowlist with JSON routes for more-context, report read/review, file, and node messages. H depends on that PR being merged and deployed, then must verify exact route shapes against the installed service before enabling those controls. Relay envelopes have a 180 KiB limit; attachment upload remains a separate pending contract. Keep oversized or unsupported attachment actions disabled with an honest unavailable state until upload is implemented and tested. No view should call the legacy local `AlondraClient` directly after H.

G1 does not change app target dependencies or navigation. H adds `//apple/Features/Questions:AlondraQuestionsFeature` to each relevant Bazel app target, then validates iOS/Mac UI flows with MAV. `ActionFeature` scopes the common question state machine for action cards; the platform view can give it different labels and layout without duplicating submission logic. Future App Intents can use `AnswerQuestionUseCase` and a headless service adapter without importing SwiftUI or a Store.
